## 新日期数据的准备

- **同一日期采 10 个校准锚点和 74 个独立 Test 点。** 每层 A/G-TR01 各一个，记录为 `train`。正式点使用既有 `TS` 编号，记录为 `test`。同层可交错采集，两组各自打包。74 个点包括基础三层 2–4F 的 54 个和 5–6F 的 20 个。
- **固定每点一条 N 朝向 Session，评分窗口 30 秒。** 从 Session 开始冷启动，按原始回调时间重放。窗口内最后一个有效新估计作为点位输出；始终等待或超时计入全分母。测试点应落图和记录实际站位。现场质量问题保留为原始记录。
- 若时间允许，以 11 月 11 日为参照约 **一周、两周**各采一轮 10+74。每轮校准和测试取同一新日期，尽量使用同一台手机并记录采集者和实际时段。每轮 Vcal10 独立从 D1 和当轮锚点拟合，便于看时间跨度对冻结 V1 与当日校准版的影响。
- 3F `B-VA01` 的原位与邻点复查、楼梯 5F→6F 与电梯 6F→4F 的真机验收使用各自工作表，沿用之前的 Train / Validation / Test 划分。详细现场步骤见 [现场执行](现场执行.md)。

正式采集前先试导出一条校准和一条 Test Session，确认 Collector 记录的时长都达到 30 秒，且两条 `labels.split` 分别为 `train` 和 `test`。旧数据每点常在 5 次回调后提前结束，需确认当前采集设置或导出方式能保留完整窗口。

## 采集回传后执行

从解压后的 `floorsense_c/` 启动 Python 3.12，并安装 `requirements.txt`。示例日期和路径改成实际采集文件。`fit` 只接收校准归档，输出模型和 `freeze.json`。冻结后才打开对应日期的 Test 归档评分。

```bash
python d3_ready/offline_check/validation_rehearsal.py --verify-freeze

python d3_ready/d3_eval.py fit --date 2026-11-18 \
  --calibration T8_D3_Calibration_2026-11-18.zip --out d3_results/2026-11-18/frozen

python d3_ready/d3_eval.py score --freeze-dir d3_results/2026-11-18/frozen \
  --test T8_D3_Test_2026-11-18.zip --out d3_results/2026-11-18/paired
```

脚本根据 `meta.json` 的日期、点号、朝向、时长和 `split` 核对归档。两版对同一批原始扫描评分，导出逐点预测、逐次更新状态、楼层与 Zone 混淆矩阵、覆盖率、West、首个正确更新时间及配对改善和退步点数。与训练资料完全相同的指纹单列供检查站位和数据来源，仍计入分母。五层目标为 **67/74**，基础三层满分线为 **49/54**。该脚本的配对分数来自归档离线重放，Android 真机展示和 App 的现场输出另外留证。

复现已有数据试跑和回归检查：

```bash
python -m unittest discover -s d3_ready -p 'test_d3_eval.py'
python d3_ready/d3_eval.py pilot --out d3_ready/pilot
```
