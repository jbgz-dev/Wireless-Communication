# D2 Validation 结果（C：静态模型，E：动态检测与融合）

日期：2026-11-10。数据：`static_validation`（15 个 VA 点，60 个 Session）和 `dynamic_validation(1)`（6 次 Run）。

## 数据标记与防泄漏

- 原始 `meta.json` 里的 `split=train` 没有改动。静态数据按 `floorsense_c/point_labels.json` 认作 Validation，脚本里逐个 Session 断言 Point ID 属于 Validation，并且楼层和区域字母与规划一致。动态数据按 Run ID（`*-VA01`）认作 Validation。
- 所有模型只用 D1 Train 训练，AP 词表也只用 Train 建立。Validation 只用来比较几种预先列好的方案，不参与训练。
- VA 扫描的指纹没有一条和训练指纹完全相同。
- 静态 VA：303 次扫描，去掉 2 次非 fresh 后剩 301 次，每点内去重后剩 89 条。主要指标用去重后的 89 条计算。
- 所有 VA 数据都是 2026-11-10 上午采集的，采集人 P2，手机 vivo V2068A，和 Train 是同一人、同一台手机。

## C：静态 Validation

### 1. D1 模型直接预测（未作任何修改）

| 模型 | 楼层 | Zone | 楼层和 Zone 都对 | West 召回率 |
|---|---|---|---|---|
| Random Forest | 91.0% | 74.2% | 71.9% | 50.0% |
| KNN | 87.6% | 61.8% | 59.6% | 19.4% |

交叉验证时 RF 楼层是 98.5%，到了新位置降到 91.0%。8 条楼层错误全部被判成 2F：

- T8-F3-B-VA01：5 条全错；
- T8-F4-B-VA01：1 条；
- T8-F4-G-VA01：2 条。

**原因：** 训练集中 T8-F2-F-TR02 有 3 条扫描只有 1、4、5 个 AP。没扫到的 AP 都填 -100，所以任何 AP 很少的新扫描，离这几条训练样本的距离都最近，就被判成 2F。F3-B-VA01 这个点只扫到 1–13 个 AP，中位数 9，而训练时同一规划位置 F3-B-TR01 能扫到 46–137 个。

### 2. 方案比较

每种方案都在 Train 上做按点分组的 5 折交叉验证（seed 42），再在 Validation 上评估：

| 方案（RF） | 交叉验证楼层 | VA 楼层 | VA Zone | VA West 召回率 |
|---|---|---|---|---|
| D1 原模型 | 98.5% | 91.0% | 74.2% | 50.0% |
| **训练时去掉 AP < 10 的扫描**（去掉 3 条） | **99.6%** | **96.6%** | 75.3% | 50.0% |
| RSSI 指数变换 | 98.5% | 91.0% | 75.3% | 52.8% |
| 去掉 AP < 10 + 指数变换 | 99.6% | 96.6% | 74.2% | 47.2% |
| 去掉 AP < 10 + 加"有没有扫到"特征 | 99.3% | 96.6% | 75.3% | 50.0% |
| 先判楼层，再在该层判 Zone | — | — | 70.8% | 38.9% |

所有方案里 KNN 都比 RF 差，VA 楼层 86.5%–88.8%，West 召回率 ≤ 28%。

**选定方案：** RF，训练时去掉 AP 少于 10 个的扫描。这个方案在交叉验证和 Validation 上都有提升，不是只对 15 个点调出来的。指数变换和"先判楼层再判 Zone"没有带来稳定提升，不采用。

### 5. 补采建议

1. **补采前先核对两件事。**
   - F3-B-VA01 为什么只扫到约 9 个 AP（训练点有 70 多个）。
   - 15 个 VA 点在规划表里的位置描述和对应 TR 点完全相同，需要确认实际距离至少 3 米。如果其实是同一位置，Validation 结果会偏乐观。
2. **补采 West 的 Train 点：** 3F、4F、6F 的 A/B 区每层 2 个新位置，共 6 个点 × N/E/S/W 四个方向，按 Train 的流程采集。这样这三层的 West 训练点从 2 个增加到 4 个。如果人力允许，2F、5F 各补 1 个，共 8 个点。新点不能和 VA、TS 点重合。
3. 可以选做：2F 在 E/F 交界补 1 个 Middle 点。
4. 楼层本身不需要大规模补采。

### 6. 给 D 的模型

- 特征处理规则不变，与 `floorsense_c/README.md` 一致。只有训练时多一条筛选：去掉 AP 少于 10 个的扫描。
- 推荐模型是 RF。但 RF 需要转成 ONNX 才能在 Android 上用，**这一步还没做**。在 ONNX 版完成并通过一致性测试之前，App 先继续用 KNN。KNN 在 VA 上的楼层准确率只有 88.8%，低于 90%。
- App 端建议：已知 AP 少于 10 个时显示"信号不足"（现在是 5 个）；投票分低于 0.4 时不更新显示。

## E：动态 Validation

### 检测方法（没有使用气压计）

- **竖直加速度：** 用 gravity 传感器确定竖直方向，把加速度计读数投影到竖直轴上。偏置用静止时段的中位数估计。
- **电梯：** 先检测启动脉冲，再找方向相反的停止脉冲。两者之间积分两次得到位移，位移除以层高 4.0 m 后取整，就是经过的层数。层高 4.0 m 是从 dynamic_train 的电梯行程算出来的，每次误差都在 ±0.3 m 以内。
- **楼梯：** 识别持续 5–30 秒的行走段。竖直加速度标准差 > 1.45 判为下楼，否则判为上楼。训练数据中上楼是 1.18–1.30，下楼是 1.66–1.82。
- **平地行走：** 行走段超过 30 秒，不算换层。
- **和 Wi-Fi 融合：** 用离散贝叶斯滤波器估计当前楼层（2–6F 的概率）。检测到换层时，用移动开始前保存的概率按换层数平移，移动途中的 Wi-Fi 不参与计算。到达后由 Wi-Fi 确认楼层。

所有阈值只在 dynamic_train 上确定，Validation 只用来检验。

### 1. 能否区分电梯上下、楼梯上下和平地行走

**Validation 6/6 全部正确，dynamic_train 20/20 全部正确。**

| Run | 真实 | 检测结果 |
|---|---|---|
| T8-EL06-VA01 | 电梯 6→4 | 电梯 −2（位移 −8.05 m） |
| T8-EL03-VA01 | 电梯 4→6 | 电梯 +2（+8.00 m） |
| T8-ST04-VA01 | 楼梯 5→6 | 楼梯 +1（标准差 1.34） |
| T8-ST08-VA01 | 楼梯 3→2 | 楼梯 −1（标准差 1.54） |
| T8-HW01-VA01 / HW02-VA01 | 平地行走 | 没有检测到换层 |

**ST08-VA01 的两个平台：** 检测器把整段楼梯当成一次行走，所以中间两个平台不会被算成两层，结果是 −1，正确。我们没有使用 `floor_passed` 的数值。

**楼梯方向的余量很小：** 两次楼梯的标准差（1.34 和 1.54）离阈值 1.45 都不远。这个阈值也只来自一个人、一台手机，换人或换手机可能失效。

### 2. 换层后能否结合 Wi-Fi 更新到正确楼层

**能。** 到达后的扫描准确率：

| 方法 | Validation | dynamic_train |
|---|---|---|
| Wi-Fi 单次扫描 | 44.4% | 71.4% |
| Wi-Fi 平滑（App 现在的做法） | 44.4% | 74.3% |
| **Wi-Fi + 传感器融合** | **94.4%** | **92.9%** |

**纯 Wi-Fi 为什么差：** 电梯厅和楼梯间信号很弱，电梯轿厢里经常只能认出 0–2 个已知 AP。到达后的前几次扫描要么没有结果，要么还停在旧楼层。

融合后，到达后显示正确楼层并保持正确所需的时间，在 Validation 上分别是：

| Run | 融合 | 纯 Wi-Fi 平滑 |
|---|---|---|
| EL06 | 0.2 s | 一直没稳定到正确楼层 |
| EL03 | 2.3 s | 4.0 s |
| ST04 | 1.0 s | 一直没稳定到正确楼层 |
| ST08 | 0.1 s | 0.1 s |

### 3. 漏检、误判和延迟

- Validation 里没有漏检，也没有误判。两次平地行走都没有产生假的换层。
- **剩下的错误都出在起点：** 在电梯厅或楼梯口打开 App 时，Wi-Fi 太弱，滤波器还不知道当前在哪层。如果起点楼层已知，比如用户从走廊走过来，那里信号好，Validation 全程准确率是 99.4%；不知道起点时是 88.5%。
- **App 端要改一处：** 不知道当前楼层时应显示"—"，不能显示概率最高的楼层。均匀分布时取最大值会落在 2F，这是滤波器的人为结果，不是真实判断。
- **时间戳核对：** 26 次 Run 的传感器数据都完整覆盖了事件时间。dynamic_train 中 EL04-TR01（6→2）检测到 3 段行程（−2、−1、−1），说明电梯中途停了两次。这就解释了之前 `floor_passed 4→3` 之间约 17 秒的空档，不是手动打点延迟。

### 4. 融合的可行性和"两种手机传感器"

融合在到达后明显好于纯 Wi-Fi：Validation 上从 44.4% 提升到 94.4%，全程从 77.6% 提升到 88.5%（不知道起点）或 99.4%（知道起点）。

**但目前还不能宣称满足"Wi-Fi + 至少两种手机传感器"。** 检测用的是加速度计，以及从加速度计派生的 gravity 和 step_detector。磁力计和陀螺仪还没有被证明有贡献。而且这台手机的陀螺仪是 `pseudo_gyroscope`，不是独立硬件。要满足这条加分项，需要再证明磁力计（或另一种传感器）带来了额外提升。可以尝试的方向：电梯轿厢里磁场幅值的变化可以用来确认电梯，楼梯平台的转身可以用 game_rotation_vector 的转角检测。

### 5. 还需要补充的动态数据

1. **楼梯连续上下两层以上：** 现在所有楼梯 Run 都只走了一层。
2. **换人或换手机：** 楼梯方向的阈值很可能需要重新设定。
3. **电梯中途停靠的 Validation 和 Test Run：** 在 Train 里出现过，Validation 里没有。
4. **楼梯走到一半折返，或在平台停留：** 用来检验误检。
5. **从走廊走进电梯或楼梯、再走出去的完整路线：** 起点要在信号好的地方，更接近真实使用场景。

## 复现

```bash
cd validation_d2
python static_validation.py         # D1 模型直接预测 → results/
python variants.py                  # 方案比较 → results/variants.csv
python variant_detail.py            # 选定方案的详细结果
cd dynamic && python fuse.py        # 动态检测 + 融合 → fusion_*.csv、detected_events.csv
```

需要 `floorsense_c` 的 Python 环境（scikit-learn 1.9.1、pandas 2.2.3），静态 Train 数据解压在 `/tmp/fs_static/sessions`。
