# FloorSense Collector：BNBU-FloorSense 数据采集 App

> **第一次使用请看 [数据采集教程.md](数据采集教程.md)**：从安装 Android Studio 到导出检查，每一步都有说明。本文件是参考资料。

这是项目的**数据采集工具**，和最终演示用的楼层识别 App 分开。原因：

- 采集时需要手动填楼层标签，而最终 App 要求“不能手动选楼层”。分开就不会混淆。
- 采集 App 记录的数据比识别 App 需要的多很多（BLE、基站、12 种传感器、跨层标记），方便以后做各个加分项。
- 你采数据的同时，队友可以独立开发识别 App 和训练模型，双方只需要约定好下面的数据格式。

`tools/fs_tools.py` 是电脑上用的脚本，负责检查数据集、合并成训练表、生成可提交的匿名数据。

---

## 1. 安装

1. 安装 [Android Studio](https://developer.android.com/studio)。
2. `File → Open`，选择 `FloorSenseCollector` 文件夹。第一次打开会自动下载 Gradle 8.7 和 Android 插件，需要联网，可能要几分钟。
3. 手机开启 **开发者选项 → USB 调试**，用数据线连电脑，点 Run ▶。
4. 第一次打开 App 时，所有权限都选“允许”。定位要选“**精确位置**”。

要求 Android 9（API 28）及以上。

## 2. 每次采集前的手机设置（很重要）

| 设置 | 位置 | 为什么 |
|---|---|---|
| **关闭 WLAN 扫描节流** | 开发者选项 → 网络 → WLAN 扫描调节 / Wi-Fi scan throttling | 不关的话每 2 分钟只能扫 4 次 |
| 打开系统定位 | 下拉状态栏 | 定位关闭时 Android 返回 0 个 AP |
| 打开 Wi-Fi 和蓝牙 | 下拉状态栏 | Wi-Fi 不用连接任何网络，开着就行 |
| 采集时 App 保持在前台 | — | 后台扫描会被系统严格限制；采集中 App 会自动保持亮屏 |

App 顶部的色条会显示环境状态：绿色表示正常，橙色表示有警告（可以继续采），红色表示不能开始。
Android 11 起，节流设置只能在开发者选项里关，`adb shell settings put global wifi_scan_throttle_enabled 0` 没有效果。
采集时界面上的“Wi-Fi 诊断”会判断扫描慢是系统限制还是 App 的问题。

## 3. 三种采集模式

### 静态定点（static）：主要的训练和测试数据
站在一个点上，按“开始采集”，App 采到“目标扫描数”次**新**的 Wi-Fi 扫描后会自动停止并响一声，点位编号自动加 1（T05 → T06）。是否自动切换朝向（N→E→S→W）和是否自动递增编号是两个独立开关。**自动递增默认关闭**，编号不会自己改变。采错的标签可以用“修改记录”修改。

### 行走（walk）：同一层内的连续数据
沿着走廊慢慢走，按“停止”结束。用来补充训练数据，也可以用来测试“信号丢失和噪声恢复”。

### 跨层（transition）：楼梯/电梯检测（加分项 A2）
1. 填当前楼层、目标楼层、方式（楼梯/电梯/扶梯），按“开始采集”。
2. **原地站 10 秒**，按“开始移动”。
3. 走楼梯时每经过一层按一次“经过一层”（可选）。
4. 到达后按“到达目标层”，**再原地站 10 秒**，按“停止”。
5. 完成后，“楼层”会自动改成目标楼层，可以直接开始下一次。

前后各站 10 秒，是为了让算法有“移动前”和“移动后”的 Wi-Fi 数据，可以证明“检测到移动后楼层自动更新”。

## 4. 防数据泄漏规则（基本分 4% 的要求）

- 训练点编号用 **T** 开头（T01, T02…），测试点用 **X** 开头（X01, X02…）。
- **测试点必须是不同的物理位置**，和任何训练点至少相距 3 米。在楼层平面图（拍照即可）上标出所有点位，报告里要用。
- App 会拒绝把已经作为 train 采过的 (楼, 层, 编号) 再作为 test 采集，反之亦然。
- 同一个测试点可以在不同日期重复采集（仍然是 test），用来评估信号随时间的变化。

## 5. 采集计划（BNBU 实际楼栋）

### 选楼

- **主楼：T5 的 2F–6F**（5 层连续，同时满足基本要求和 A1）。T6、T7 的情况一样，选哪栋都行，换一下楼名即可。
- **第二栋楼（A6）：T29**。它和 T4–T7 不相连，AP 重叠少。
- 已知情况：T4–T7 在 2F–6F 由连廊相连，T8 只在 4F 相连；每栋楼有两部电梯；没上课时课室可以进，晚上也能进楼。

### 连廊的影响

- 每一层都能扫到隔壁楼同一层的 AP。这对**判断楼层有帮助**，因为同一层能看到的 AP 更多。
- 对**判断在哪栋楼（A6）不利**，因为连廊附近两栋楼的信号很像。处理方法：
  - 在连廊上取的点，"楼名"填你所在那一侧的楼，"区域"填 `bridge-T5T6` 或 `bridge-T4T5`；
  - 写 A6 报告时，把连廊附近的点单独统计准确率。
- 1F 和 7F 没有连廊，信号特征和 2F–6F 不一样。如果以后要加 1F 或 7F，需要单独采足训练点。

### 每层怎么取点（2F–6F，每层都一样）

开始前，先**拍下每层电梯口的消防疏散图**，在图上标出所有点位的位置和编号，报告里要用到。

**训练点 15 个（T01–T15）**：

| 位置 | 数量 | 区域填写 |
|---|---|---|
| 两部电梯门口 | 各 1 个 | `lift` |
| 每个楼梯口 | 各 1 个 | `stair` |
| 走廊，每隔约 8–10 米一个，两端都要有 | 5–6 个 | `corridor` |
| 两侧连廊入口 | 1–2 个 | `bridge-T5T6` 等 |
| 课室里面 | 3–4 个 | 课室号，如 `501` |

**测试点 12 个（X01–X12）**：放在训练点之间，并且和任何训练点至少相距 3 米。可以选：走廊上两个训练点的中间、课室后排、窗边、没取过训练点的课室。其中至少 3 个在课室里，2 个在电梯或楼梯附近，1–2 个在连廊上。

5 层 × 12 个 = **60 个测试点**，满足 ≥50 的要求。

T5 各层的课室（来自教务处课室表）：2F：201、202；3F：301、302、304、306、307；4F：401、402、404、405、406；5F：501–505；6F：601–605。2F 只有两间课室，走廊和连廊的点要多取一些。

### 时间安排

| 轮 | 内容 | 什么时候 | 手机 / 采集人 | 预计用时 |
|---|---|---|---|---|
| 1 训练 | 每个点 4 个朝向 × 5 次扫描，再加 1 次"裤袋"；每层 2 条行走路线 | 第 1 天，白天 | 手机 A / P1 | 每层约 35 分钟，5 层约 3 小时，可以分两次 |
| 2 测试 | 每个点 1 次，目标扫描数 10，朝向和持机方式随机 | 第 3–4 天，**晚上** | 手机 A / P1 | 每层约 10 分钟 |
| 3 跨层 | 两部电梯上、下各至少 5 次，"备注"填 `电梯A` 或 `电梯B`，并包含跨多层的情况；楼梯：每对相邻楼层上、下各 2 次，再加几次跨 2 层的 | 任何时候 | 手机 A | 约 40 分钟 |
| 4 第二部手机 | 训练点只采 1 个朝向，测试点全部重采 | 第 2–5 天 | 手机 B / P2 | 每层约 15 分钟 |
| 5 一周后 | 测试点全部重采；每层再采 3 个新训练点（T21–T23），用来证明少量重新校准就能恢复准确率 | 第 8 天以后，换一个时段 | 手机 A | 约 1.5 小时 |
| 6 T29 | 连续 3 层（如 2F–4F），每层 8 个训练点（2 个朝向）和 6 个测试点 | 任何时候 | 手机 A | 约 1.5 小时 |

- 训练和测试安排在**不同的日子和时段**（白天训练、晚上测试）。这正好满足评分要求里的"多个时间"，也更能说明模型不是只记住了某个时刻的信号。
- 课间人多的时候也可以采，在"备注"里写上"人多"。
- 时间充裕的话，可以把 1F 和 7F 也加进来，变成 7 层，A1 的证据会更充分。

每轮结束后：**导出 → 拷到电脑 → 运行 `check`**，发现问题当天就能补采。

## 6. 导出数据

- App 里按“导出全部”，打包成 zip，可以发到微信、网盘等。
- 或者用数据线连电脑，在手机存储里找到：
  `Android/data/edu.bnbu.floorsense.collector/files/sessions/`
- 多部手机的数据解压到同一个上级目录即可，脚本会递归查找。

## 7. 电脑端脚本

只需要 Python 3.8+，不需要安装任何库。

```bash
# 检查：每层覆盖、测试点数量、数据泄漏、数据质量、加分项准备情况
python tools/fs_tools.py check data/

# 合并成一张 Wi-Fi 长表，给训练模型的同学用
python tools/fs_tools.py merge data/ -o wifi_scans.csv

# 生成可以提交的匿名数据集（BSSID、SSID、BLE 地址、基站号做 HMAC 哈希，删除备注）
python tools/fs_tools.py anonymize data/ -o data_anon/ --salt 组内自定的一串字符
```

`check` 有 ERROR 时退出码为 1。数据泄漏、全部 0 个 AP、出现气压计数据都算 ERROR。

## 8. 数据格式

每次采集是一个目录，名字是 `时间_楼_层_模式_点位_采集人`，里面有：

| 文件 | 内容 |
|---|---|
| `meta.json` | 标签（楼、层、区域、点位、split、模式、朝向、持机、跨层目标）、机型、Android 版本、开始时环境、统计 |
| `wifi.csv` | 每次扫描每个 AP 一行：`scan_id, t_wall_ms, t_elapsed_ms, fresh, n_ap, bssid, ssid, rssi, freq_mhz, channel_width, wifi_standard, age_ms` |
| `ble.csv` | 每个 BLE 广播包一行：`address, rssi, tx_power, connectable, ibeacon_uuid/major/minor/tx` |
| `cell.csv` | 每 2 秒每个可见基站一行：`type(lte/nr/gsm/wcdma), registered, mcc, mnc, area, cid, pci, arfcn, dbm, rsrp, rsrq, sinr, level` |
| `sensors.csv` | 约 50 Hz，一行一个事件：`t_ns, sensor, v0..v5, accuracy` |
| `sensors.json` | 这部手机实际可用的传感器型号、精度、量程 |
| `events.csv` | 会话开始/结束、`move_start`、`floor_passed`、`move_end`、扫描被拒绝等 |

要点：

- **只用 `fresh=1` 的扫描**。`fresh=0` 是系统返回的缓存结果，和上一次重复。
- `results_updated` 是系统广播里的 `EXTRA_RESULTS_UPDATED`。0 表示系统这次没有真正扫描，只把旧结果再发了一遍，这就是节流的特征。
- `meta.json` 的 `stats` 里有 `wifi_scan_requests`（请求次数）、`wifi_results_not_updated`（回旧结果次数）、`wifi_mean_fresh_interval_s`（新扫描平均间隔）。
- 在手机上改过标签的记录会有 `label_history` 和 `labels_modified_ms`。电脑端脚本遇到同一记录有多个版本时，会采用最后修改的那一份。
- `bssid` 为空的行表示这次扫描一个 AP 都没扫到（真实的信号丢失）。
- `status` 为 `incomplete` 的会话是中途手动停止的，`merge` 默认跳过。
- 时间对齐：`wifi/ble/cell` 的 `t_elapsed_ms` × 10⁶ 和 `sensors.csv` 的 `t_ns` 用的是同一个时钟（开机后经过的时间）。
- 传感器有：`acc, lin_acc, gravity, gyro, mag, mag_uncal, rot_vec, game_rot_vec, light, proximity, step_detector, step_counter`。**按课程要求不记录气压计。**

## 9. 数据和加分项的对应关系

| 评分项 | 需要的数据 | 采集计划 |
|---|---|---|
| 基本 12%：三层识别 | 各层训练点 + ≥50 个测试点 | 第 1、2 轮 |
| 基本 4%：实时、抗信号丢失 | 行走数据、0 AP 扫描记录 | 第 1 轮行走 |
| 基本 4%：评估可复现 | 多位置、多时段、多朝向，train/test 分开 | 第 1、2 轮 + 防泄漏检查 |
| A1 五层 2% | ≥5 层连续楼层 | 第 1、2 轮 |
| A2 楼梯/电梯 3% | 带 move_start/move_end 标记的跨层记录 + 加速度/陀螺仪/计步 | 第 3 轮 |
| A3 传感器融合 3% | 磁力计、光线等，和 Wi-Fi 在同一会话里同步记录 | 所有轮次自动记录 |
| A4 多用户多机型 3% | 两种机型、两位采集人 | 第 4 轮 |
| A5 随时间变化 3% | 间隔一周的测试数据 + 少量新训练点 | 第 5 轮 |
| A6 多栋楼 5% | 第二栋楼 ≥3 层 | 第 6 轮 |
| A7 区域 / 隐私 3% | 区域标签；匿名化脚本 | 每次填区域；`anonymize` |

## 10. 隐私说明（报告可以引用）

- App 不记录 BLE 设备名、GPS 坐标、用户真名；采集人只用代号。
- 原始数据只保存在手机的 App 私有目录，导出需要手动操作。
- 提交的数据集用 `anonymize` 处理：AP 的 BSSID/SSID、BLE 地址、iBeacon UUID、基站区号和小区号都换成 HMAC-SHA256 代号。salt 不公开，所以无法反查真实地址；同一个 salt 下映射是一致的，匿名数据仍能复现训练结果。
